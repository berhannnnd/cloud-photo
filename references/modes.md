# 两种用户模式

顶层 Skill 先判断用户是在建立索引，还是要根据目标整理照片。两种模式共享 manifest，但入口、输出和写权限不同。

## 模式 A：建立索引

触发语句包括“把这里的照片索引一下”“扫描照片”“给相册建立索引”“更新照片标签”。

处理流程：

1. 通过 `cloud-access` 分页发现照片并读取文件元数据。
2. 生成或复用缩略图，写入 `thumbnail_tags`。
3. 分批请求多模态模型，写入 `vision_tags`。
4. 合并 manifest，保存 checkpoint 和批次报告。
5. 返回已扫描、已完成、待重试的数量，以及 manifest 位置。

此模式只建立或更新索引，不移动、重命名、删除照片，也不替用户创建相册。

## 模式 B：按要求整理

触发语句包括“帮我整理猫的照片”“把旅行照片归到相册”“找出重复照片并整理”“把某一批照片移动到目录”。

处理流程：

1. 先检查 manifest 是否存在且不过期；缺少索引时，先建议或执行模式 A 的必要增量索引。
2. 把用户目标拆成查询条件，使用 `index-guidance` 检索候选。
3. 对需要准确判断的候选图片进行多模态复核。
4. 生成**整理预览计划**：先展示候选图片，再列出目标相册/目录、拟执行的复制/建册操作和无法判断的项目。文件层面不承诺移动、删除或重命名；整理到目录使用 `files copy`，原图保留。
5. 等用户确认后，才调用 `cm-cloud-manage` 执行云盘写操作。
6. 执行后先查询异步 operation 的逐项结果，再按真实回执和目标目录重新列目录对账；更新 manifest 中的路径、相册和更新时间。未知结果进入待核对状态，不自动重放。

整理模式可以读取索引，但不能把“整理”误当成“重新索引”；只有索引缺失或用户明确要求更新标签时才进入模式 A。

## 路由优先级

- “索引、扫描、打标签、建立照片库” → 模式 A。
- “整理、归类、移动、归档、创建相册、找出后处理” → 模式 B。
- 同一句同时包含两类意图时，先完成模式 A 的必要索引，再停在模式 B 的预览计划，不直接执行写操作。
